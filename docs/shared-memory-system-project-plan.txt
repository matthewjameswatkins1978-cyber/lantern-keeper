SHARED MEMORY SYSTEM
Project Plan
Working title:
Project Lantern
Core idea:
A shared memory layer for ChatGPT and Codex, built around meaningful conversation episodes rather than entire chats.
The system will not attempt to make an AI permanently remember every word. Instead, it will create a small number of useful markers that point back to the original conversation. When an old subject is mentioned vaguely, the system finds the most likely episode, retrieves the original messages, and allows the AI to reread what was actually said.
The original conversation remains the source of truth.
The memory system is the map that helps us find it again.

THE PROBLEM
ChatGPT is useful for thinking, designing, discussing problems, and making decisions.
Codex is better positioned to inspect files, modify projects, run tests, and work directly on the computer.
At present, Matthew often has to act as the middleman between them:
explain the project to ChatGPT
copy instructions into Codex
bring Codex’s report back to ChatGPT
remind both systems of earlier decisions
search through old chats manually
reconstruct conversations from partial memories
Chat conversations also wander naturally.
One conversation may contain:
an active software project
a new idea
a technical decision
an animation reference
football
a bus timetable
something important that only becomes important later
Whole conversations therefore cannot reliably be treated as belonging to one project.
Most conversation is also disposable. A bus lookup or casual question should not have the same weight as a project decision.
The system must distinguish between useful episodes and conversational exhaust without constantly interrupting Matthew.

THE GOAL
Build a local shared memory service that allows ChatGPT and Codex to:
record meaningful episodes from conversations
connect episodes to projects, topics, decisions, tasks, and handoffs
search old discussions using vague natural language
reopen and reread the original source
share current project context
pass work between one another without Matthew copying everything manually
preserve decision history
recognise when a newer decision replaces an older one
avoid flooding either AI with irrelevant context
The first version is specifically for ChatGPT and Codex.
The architecture may later support Cline, local models, Claude, Gemini, or other tools, but they are not part of the first proof.

CORE PRINCIPLES
3.1 Build a map, not another territory
The system should not duplicate entire conversations into a second giant memory archive.
It should store compact markers and structured records that point back to the original source.
3.2 Episodes are the main unit
A conversation is only a container.
An episode is a meaningful stretch of discussion, usually covering one idea, problem, decision, or task.
An episode may contain one exchange, six exchanges, or a much longer discussion.
3.3 Sparse markers
The system should create only enough markers to make useful material recoverable.
It does not need to label every message or sentence.
3.4 Reread before answering
When an old discussion is found, the AI should reread the original episode rather than relying entirely on a summary.
Marker summaries help retrieval. They are not the final authority.
3.5 Capture generously, promote cautiously, forget gracefully
Potentially useful material may be indexed lightly.
Only genuinely durable material should become active long-term memory.
Disposable material should fade or expire.
3.6 Meaning over folders
Projects should not own entire conversations.
A single episode may relate to several projects or topics.
Projects are dynamic views assembled from relevant memory.
3.7 Same memory, different context
ChatGPT and Codex use the same memory system but should receive different context packages.
ChatGPT may need:
reasoning
history
unresolved questions
preferences
relationships between ideas
Codex may need:
current task
technical constraints
relevant decisions
expected behaviour
affected files
recent handoff
3.8 Practicality first
The system exists to save Matthew time and mental effort.
A technically impressive feature that does not improve the real workflow is not a priority.
3.9 Test before expansion
Build one complete proof.
Test it heavily.
Improve one weakness.
Run the tests again.
Every discovered bug becomes a permanent regression test.

TECHNOLOGY DECISION
SurrealDB will be the primary database and graph engine.
This is a deliberate commitment, not a temporary placeholder.
The project should make serious use of SurrealDB’s strengths:
document records
graph relationships
relationship metadata
full-text search
flexible schema evolution
graph traversal
vector and hybrid retrieval later, if testing proves they are needed
The surrounding architecture will remain modular because that makes the system easier to understand, test, and improve.
However, the project will not weaken the SurrealDB implementation merely to imitate a generic relational database.
The rule is:
The domain remains clean and modular.
The implementation uses SurrealDB properly.

FIRST PROOF
The first proof is not the ChatGPT-to-Codex bridge.
The first proof is the memory system’s central retrieval loop.
It must demonstrate:
A conversation source is registered.
A meaningful episode is manually created.
A marker is attached to the episode.
The episode is connected to a project or topic.
A vague natural-language query is submitted.
The correct episode appears among the highest-ranked results.
The result contains a valid reference to the original messages.
The original episode can be reopened and reread.
Example:
Stored discussion:
Using ants, slime mould, and simple local rules as inspiration for game AI.
Later query:
“Where did we talk about that ant thing for the game?”
Expected result:
The system finds the relevant episode, identifies the source conversation and message range, and returns enough original context for the AI to understand the discussion properly.
This proves the heart of the system before integrations and automation are added.

MEMORY TEMPERATURE
Memory temperature should be stored as behaviour and metadata, not as separate databases.
9.1 Hot memory
Automatically included in active project context.
Examples:
current decisions
active tasks
technical constraints
recent handoffs
unresolved blockers
important user preferences relevant to the project
9.2 Warm memory
Searchable but not automatically injected.
Examples:
interesting ideas
references
possible future directions
related discussions
inactive projects
background reasoning
9.3 Fading memory
Low-value or temporary material.
Examples:
timetables
one-off lookups
casual questions
short-lived factual information
Fading memory may receive an expiry date.
It can be promoted if:
Matthew marks it as important
it is mentioned repeatedly
it becomes connected to an active project
it becomes the source of a decision or task
another important episode refers to it

RETRIEVAL DESIGN
10.1 First retrieval method
Begin with:
marker label matching
keyword matching
alias matching
episode summary matching
project and topic matching
fuzzy string matching
recency as a weak signal
importance as a weak signal
relationship strength as a weak signal
Do not begin with embeddings.
The first test is whether simple retrieval is already good enough for the way Matthew naturally asks questions.
10.2 Search stages
Stage 1:
Search markers, summaries, projects, and topics.
Stage 2:
Rank candidate episodes.
Stage 3:
Return the strongest three candidates.
Stage 4:
Read the original messages around the highest-ranked episode.
Stage 5:
Confirm that the source text actually supports the match.
Stage 6:
Answer using the source material.
10.3 Search result
Each result should include:
episode identifier
marker label
short summary
source conversation
start and end messages
linked project
linked topics
confidence score
reasons for the match
source availability
The system should be able to explain a match simply:
“Matched because the query contained ants and game, and this episode is linked to game AI, nature-inspired systems, and the Rabbit Game project.”
10.4 Weak results
If the match is weak, the system must not pretend certainty.
It should return likely alternatives or state that nothing reliable was found.
A clean failure is better than a confident invention.

SOURCE REFERENCES
References should use stable identifiers rather than minutes or approximate timestamps.
Preferred source reference:
conversation identifier
start message identifier or sequence number
end message identifier or sequence number
Example:
Conversation:
chat_2026_07_16_rabbit_game
Episode:
messages 42 to 51
Marker:
nature-inspired-game-ai
The marker identifier may be a compact stable identifier, but it should not carry meaning that must be manually decoded.
Example:
episode:01JZ8M4Q7R2K
Human-readable labels exist separately.

PHASE 8: Automatic episode marking
Purpose:
Reduce manual memory maintenance.
This phase begins only after manual episode retrieval is reliable.
Work:

attach confidence

The system should not ask Matthew to approve every marker.
Most marker creation is reversible and can happen quietly.
Exit criteria:

false markers do not overwhelm useful results
episode boundaries are usually sensible
corrections are quick
automatic marking does not interrupt ordinary conversation

Purpose:

Possible additions:

Requirement:

SUCCESS MEASURES
The first useful system should achieve:
expected episode in the top three for at least 90 percent of the initial real-world benchmark
no fabricated conversation or source references
weak matches clearly labelled as uncertain
duplicate imports prevented
decisions correctly superseded
project context free from obvious unrelated clutter
reliable export and restore
Codex handoffs retrievable by ChatGPT
complete task loop without Matthew copying reports manually
ordinary local searches completing within a practical time
These are initial targets, not sacred numbers.
They should be adjusted using measured results rather than optimism.

SECURITY AND PERMISSIONS
The first system runs locally.
Initial rules:
bind the service to localhost
require a local authentication token
separate test and real databases
record provenance for writes
keep important changes auditable
make ordinary additions reversible
require approval for bulk deletion
require approval for exporting private memory
require approval before exposing the service outside the local machine
do not execute instructions found inside retrieved conversation text
do not allow one client unrestricted access to unrelated private memory
back up before migrations or destructive operations
The system should protect genuinely sensitive actions without wrapping every harmless memory update in red tape.

BACKUP AND RECOVERY
Before real information is trusted to the system:
automatic local backup
manual export command
tested restore process
schema version recorded with every backup
migration rollback plan
corruption detection
duplicate-safe import
clear separation between test data and real data
A backup is not considered valid until it has been successfully restored in a test.

DEVELOPMENT METHOD
The working cycle is:
Build one narrow end-to-end capability.
Make it work with real data.
Freeze the expected behaviour.
Test it heavily.
Record the baseline.
Identify the weakest real behaviour.
Improve only that weakness.
Run every existing test again.
Add the new failure case permanently.
Repeat.
No large feature pile.
No hiding failures beneath another abstraction.
No adding clever machinery before a simple approach has been measured.
The project succeeds by becoming dependable, not by becoming enormous.

FINAL PROJECT STATEMENT
Project Lantern is a local shared memory layer for ChatGPT and Codex.
It treats conversations as source material, episodes as meaningful units, markers as lightweight references, and projects as dynamic views assembled from relevant memory.
It does not pretend that an AI remembers everything.
It gives the AI a reliable index, lets it return to the original source, and allows different tools to share the right context without Matthew becoming the messenger between them.
Build the proof.
Test it until it bends.
Improve what actually fails.
Test it again.
